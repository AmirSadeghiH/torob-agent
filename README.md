# هم‌خرید — دستیار خرید حضوری تهران

اپلیکیشن وب موبایل‌فرست برای خرید حضوری: از یک پیام فارسی تا کالای واقعی، مقایسهٔ
فروشندگان، فروشگاه‌های نزدیک با ساعت کاری، و یک برنامهٔ خرید پیاده‌روی‌شدنی.
تمام پاسخ‌ها از دیتاست واقعی (۲۲۵٬۹۰۳ کالا، ۳۱۴٬۶۱۲ پیشنهاد، ۶٬۴۷۶ فروشگاه) می‌آید.

Stack: React + TypeScript (strict) + Vite + Tailwind + Vibe Farsi + Express + SQLite/FTS5.

## راه‌اندازی

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt   # یک‌بار
npm install
npm run data:import        # ساخت data/hamkharid.db از فایل‌های CSV (۶۳۸ هزار ردیف، idempotent)
npm run dev                # API روی 8787 و رابط کاربری روی 5173
```

`npm run dev` هر دو فرایند را با هم بالا می‌آورد. برای دمو:

```bash
npm run build && npm start   # یک پورت: http://127.0.0.1:8787 با dist/ سرو می‌شود
```

متغیرهای محیطی اختیاری: `PORT` (پیش‌فرض 8787)، `HAMKHARID_DB` (مسیر فایل دیتابیس).
این‌ها و متغیرهای دستیار مدل‌زبانی از `.env` در سمت سرور خوانده می‌شوند (الگوی کامل: `.env.example`).
هیچ کلید API لازم نیست؛ بدون کلید، همان دستیار محلی و قطعی پاسخ می‌دهد.

## دستیار مدل زبانی (اختیاری)

وقتی `AI_AGENT_ENABLED=true` باشد و کلید معتبری تنظیم شده باشد، `/api/assistant` به‌جای
مسیر قاعده‌محور، یک ایجنت واقعی LangChain را اجرا می‌کند:

```env
AI_AGENT_ENABLED=true
OPENAI_API_KEY=                # کلید خودت را در .env بگذار، هرگز commit نشود
OPENAI_MODEL=gpt-5.6-sol
OPENAI_BASE_URL=               # فقط برای endpoint سازگار با OpenAI
AI_AGENT_FALLBACK_TO_RULES=true
AI_AGENT_MAX_STEPS=4
```

- **مدل:** `ChatOpenAI` از `@langchain/openai` با شناسهٔ دقیق `gpt-5.6-sol`، روی Responses API
  (`useResponsesApi: true`) و با `reasoning.effort = "low"`. مدل و آدرس سرویس قابل تنظیم‌اند.
- **حلقهٔ ایجنت:** `createAgent` از `langchain` (بر پایهٔ LangGraph). مدل خودش انتخاب می‌کند
  کدام ابزار را صدا بزند، نتیجهٔ واقعی ابزار را می‌خواند و در صورت نیاز ابزار بعدی را
  انتخاب می‌کند. سقف گام‌ها با `toolCallLimitMiddleware` و `recursionLimit` اعمال می‌شود.
- **ابزارها (Zod):** `search_products`، `get_product_details`، `compare_products`،
  `find_stores_for_product`، `find_alternatives`، `build_shopping_plan`، `get_shop_details`.
  هر ابزار روی `server/repo.ts` و `server/plan.ts` می‌نشیند، ورودی را اعتبارسنجی می‌کند و
  فقط رکوردهای واقعی دیتاست را برمی‌گرداند.
- **رابط تولیدی:** مدل فقط متن فارسی می‌نویسد؛ بلوک‌ها (`products`، `offers`، `compare`،
  `stores`، `map`، `insight`، `plan`) در سرور و فقط از نتایج ابزارها ساخته می‌شوند. هر درخواست
  جمع‌آورندهٔ مستقل خودش را دارد (`AsyncLocalStorage`)، پس درخواست‌های هم‌زمان قاطی نمی‌شوند.
- **شفافیت موتور:** پاسخ‌ها `meta.engine` را برمی‌گردانند: `llm_agent` (مدل ابزار را اجرا کرد)،
  `rules_fallback` (دستیار قطعی جواب داد)، یا `rules` (ایجنت خاموش است). `meta.tool_calls`
  فقط ابزارهایی است که واقعاً اجرا شده‌اند.
- **تاریخچهٔ گفت‌وگو:** کلاینت حداکثر ۶ نوبت اخیر را در `history` می‌فرستد و سرور آن را
  دوباره محدود و پاک‌سازی می‌کند؛ همین برای «همین رو ارزون‌تر پیدا کن» و «برنامهٔ خرید بچین» کافی است.

بدون کلید یا با خطای مدل، اگر `AI_AGENT_FALLBACK_TO_RULES=true` باشد همان دستیار قطعی پاسخ
می‌دهد و پاسخ صادقانه `rules_fallback` علامت می‌خورد؛ خطا فقط به‌صورت خلاصه و بدون کلید یا
payload در لاگ سرور ثبت می‌شود. با `false` شدن این متغیر، خطای مدل به کلاینت برمی‌گردد.

## بررسی و تست

```bash
npm test                              # ۳۳ تست: NLU، تازگی قیمت، جغرافیا، ساعت کاری، اتکا، و حلقهٔ ایجنت با مدل ساختگی
npm run typecheck && npm run build    # strict TS + build تولید
python scripts/smoke_api.py           # ۳۳ بررسی سرتاسری روی HTTP API در حال اجرا
AI_AGENT_LIVE_TEST=1 npm test         # فقط با کلید معتبر: یک تماس واقعی مدل + ابزار
python scripts/inspect_dataset.py     # بازتولید docs/dataset-audit.md
```

## چه چیزی ساخته شده

**گفت‌وگو با رابط تولیدی (Generative UI).** پیام فارسی به intent، دسته، برند، محله و
بودجه تبدیل می‌شود و دستیار بلوک‌های تعاملی می‌سازد، نه متن: کارت کالا، جدول
پیشنهاد فروشندگان، مقایسهٔ ستونی، فهرست و نقشهٔ فروشگاه، تفکیک امتیاز اتکا، فیلترهای
قابل تغییر، و برنامهٔ خرید. هر پاسخ `tool_calls` واقعی خود را برمی‌گرداند
(`search_products`، `get_product`، `search_shops`، `get_stores_selling`، `build_plan`).

**موتور NLU بدون مدل زبانی.** تطبیق کل‌واژه با واژگان دیتاست (دسته‌ها، برندها، محله‌ها)،
مترادف‌های محاوره‌ای («هندزفری» → «هدفون»)، جمع‌های فارسی («هدفون‌ها»)، بودجه با
واحدهای میلیون/میلیارد/هزار و بازه («بین ۱۰ تا ۲۰ میلیون»). اعداد فارسی و لاتین،
ی/ك عربی و نیم‌فاصله نرمال می‌شوند؛ «سلام» دیگر به «سلامت» و «بچین» به «سیم چین» وصل نمی‌شود.

**تازگی و اتکای قیمت.** هر پیشنهاد سن قیمت، امتیاز اتکای ۰–۱۰۰ با سیگنال‌های
قابل مشاهده (تازگی، راه ارتباطی فروشگاه، گارانتی، پرت بودن قیمت از بازار) و برچسب
«تازه/قابل اتکا/قدیمی/کهنه» دارد. برنامهٔ خرید هشدار «تلفنی تأیید بگیرید» را از همین‌جا می‌سازد.

**جست‌وجو و کاوش.** جست‌وجوی FTS5 با پیشوند، فیلتر دسته/برند/محله/بازهٔ قیمت/حداقل
تعداد فروشنده/حداکثر سن قیمت، شعاع مکانی، مرتب‌سازی و صفحه‌بندی. جست‌وجوی
متنی روی دیتابیس ۵۳۰ مگابایتی ۱۲ تا ۱۱۰ میلی‌ثانیه طول می‌کشد (اندازه‌گیری‌شده
روی شش پرس‌وجوی رایج، شامل زمان شمارش کل).

**فروشگاه‌ها و نقشه.** فهرست فروشگاه‌ها با فاصله از نقطهٔ شروع، شعاع، دسته و محله،
ساعت کاری هفتگی زندهٔ تهران (باز/بسته/نامشخص)، راه‌های تماس، و نقشهٔ شماتیک با
مختصات واقعی. نقطهٔ شروع را از فهرست محله‌ها یا موقعیت مکانی مرورگر انتخاب می‌کنید.

**برنامهٔ خرید حضوری.** سبد (۰ تا ۲۵ قلم) بر اساس فروشگاه گروه‌بندی می‌شود، ایست‌ها
با نزدیک‌ترین همسایه از مبدأ مرتب می‌شوند و زمان پیاده‌روی، جمع سبد، فاصلهٔ هر ایست و
هشدارهای تازگی محاسبه می‌شود. سبد، نقطهٔ شروع و گفت‌وگو در `localStorage` می‌مانند.

```
  lib/           تازگی قیمت، جغرافیا (haversine/bbox/مسیر)، ساعت کاری، نرمال‌سازی متن فارسی، بارگذاری env
  tests/         تست‌های node:test

```

## داده

`scripts/import_dataset.py` سه CSV را در یک پاس جریانی می‌خواند، ردیف‌های نامعتبر
(قیمت غیرمثبت، تاریخ بد، مختصات بیرون تهران) را رد یا علامت‌گذاری می‌کند و دیتابیس را
اتمی می‌سازد؛ اجرای دوباره رکورد تکراری نمی‌سازد. جزئیات کیفیت داده، شمارش‌ها و
نگاشت ستون‌ها در [docs/dataset-audit.md](docs/dataset-audit.md).

فایل‌های CSV، `.venv` و `data/*.db` در Git نیستند؛ دیتاست اصلی هرگز بازنویسی نمی‌شود.

## محدودیت‌های آگاهانه

- موجودی و قیمت «زنده» تأیید نمی‌شود؛ همه‌چیز از تاریخ `last_price_changed_at` دیتاست می‌آید.
- ۴۱٪ فروشگاه‌ها هیچ پیشنهادی در دیتاست ندارند و ۲,۶۸۴ فروشگاه بدون کالا در فهرست می‌مانند.
- برنامهٔ خرید با «نزدیک‌ترین همسایه» چیده می‌شود، نه حل دقیق TSP؛ برای ۲ تا ۶ ایست کافی است.
- جست‌وجوی شعاعی ابتدا با bbox در SQL غربال و سپس با فاصلهٔ دقیق مرتب می‌شود (سقف ۵۰۰ کاندید).
- عکس کالاها از دامنهٔ خارجی می‌آید؛ در نبود شبکه، جای‌نگهدار حرف اول برند نمایش داده می‌شود.
- دستیار LLM اختیاری است. در این محیط کلید معتبر وجود نداشت، پس حلقهٔ واقعی مدل با یک API زنده تأیید نشده؛ کل حلقه (انتخاب ابزار، اجرای ابزار، بازگشت نتیجه به مدل، ساخت بلوک) با مدل ساختگی تست شده است.
- متن پاسخ مدل ممکن است لحن ثابتی نداشته باشد؛ داده و بلوک‌ها همیشه از سرور می‌آیند، ولی کیفیت جمله‌بندی مدل تضمینی نیست.
